# A03 - Injection (SQL/JS)

## Comment on a protégé l'app contre les injections

### Le problème

Les injections SQL/JS permettent d'exécuter du code malveillant via les inputs utilisateur. Sans protection :

- Un attacker peut lire/modifier/supprimer toute la BDD
- Du code JavaScript malveillant peut être exécuté
- Les données sensibles peuvent être exposées

### Notre solution

#### 1. ORM Sequelize (protection SQL)

Fichier : `src/models/` + `src/controllers/`

On utilise Sequelize qui protège automatiquement contre les injections SQL avec des requêtes préparées.

**Exemples sécurisés :**

```javascript
// ✅ SÉCURISÉ - Sequelize utilise des requêtes préparées
const user = await User.findByPk(id);
const animal = await Animal.findOne({ where: { name: userInput } });
const animals = await Animal.findAll({
  where: {
    species: req.query.species,
  },
});

// ✅ SÉCURISÉ - Création avec validation
const animal = await Animal.create({
  name,
  species,
  breed,
  age: parseInt(age), // Cast sécurisé
  id_association: req.user.id_association,
});

// ✅ SÉCURISÉ - Mise à jour
await animal.update({
  name: name || animal.name,
  status: status || animal.status,
});
```

**Ce qu'on évite (vulnérable) :**

```javascript
// ❌ VULNÉRABLE - Requête SQL brute
const query = `SELECT * FROM animal WHERE name = '${userInput}'`;
db.query(query); // Injection possible !

// ❌ VULNÉRABLE - Concaténation directe
const sql = "DELETE FROM user WHERE id = " + userId;
```

**Pourquoi Sequelize protège :**

- Requêtes préparées automatiques
- Échappement des caractères spéciaux
- Validation des types de données
- Pas de concaténation directe de strings

#### 2. Validation stricte avec Express-Validator

Fichier : `src/middlewares/validation.js`

On valide et nettoie tous les inputs avant qu'ils atteignent la BDD.

**Validation des utilisateurs :**

```javascript
export const validateRegister = [
  body("first_name")
    .trim() // Supprime espaces
    .isLength({ min: 2, max: 100 })
    .withMessage("Le prénom doit contenir entre 2 et 100 caractères"),

  body("email")
    .isEmail()
    .normalizeEmail() // Normalise format email
    .withMessage("Email invalide"),

  body("password")
    .isLength({ min: 8 })
    .matches(/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)/)
    .withMessage("Password trop faible"),
];
```

**Validation des animaux :**

```javascript
export const validateAnimal = [
  body("name").trim().isLength({ min: 1, max: 100 }).withMessage("Nom requis"),

  body("age")
    .optional()
    .isInt({ min: 0 })
    .withMessage("L'âge doit être un entier positif"),

  body("status")
    .optional()
    .isIn(["disponible", "accueilli"]) // Whitelist
    .withMessage("Statut invalide"),

  body("photo_url").optional().isURL().withMessage("URL invalide"),
];
```

**Validation des demandes :**

```javascript
export const validateRequest = [
  body("message")
    .optional()
    .trim()
    .isLength({ max: 1000 })
    .withMessage("Message trop long"),

  body("id_animal").isInt({ min: 1 }).withMessage("ID animal invalide"),
];
```

#### 3. Application des validations dans les routes

Les validations sont appliquées avant les contrôleurs :

```javascript
// src/routes/animals.js
router.post(
  "/",
  authenticateToken,
  requireRole("association"),
  validateAnimal, // ← Validation avant contrôleur
  createAnimal
);

// src/routes/auth.js
router.post(
  "/register",
  validateRegister, // ← Validation
  register
);

// src/routes/requests.js
router.post(
  "/",
  authenticateToken,
  requireRole("foster"),
  validateRequest, // ← Validation
  createRequest
);
```

#### 4. Gestion des erreurs de validation

Fichier : `src/middlewares/validation.js`

```javascript
export const handleValidationErrors = (req, res, next) => {
  const errors = validationResult(req);
  if (!errors.isEmpty()) {
    return res.status(400).json({
      success: false,
      message: "Données invalides",
      errors: errors.array(),
    });
  }
  next();
};
```

#### 5. Contraintes au niveau modèle

Fichier : `src/models/User.js` (exemple)

```javascript
const User = sequelize.define("User", {
  email: {
    type: DataTypes.STRING(100),
    allowNull: false,
    unique: true,
    validate: {
      isEmail: true, // Validation Sequelize
    },
  },
  password: {
    type: DataTypes.TEXT,
    allowNull: false,
  },
  id_role: {
    type: DataTypes.INTEGER,
    allowNull: false,
    references: {
      model: Role,
      key: "id_role",
    },
  },
});
```

### Ce qu'on a sécurisé

- **Requêtes SQL** : Sequelize ORM avec requêtes préparées
- **Inputs utilisateur** : Validation + sanitisation express-validator
- **Types de données** : Cast sécurisé (parseInt, isInt, isEmail)
- **Longueurs** : Limites sur tous les champs texte
- **Formats** : Validation email, URL, patterns
- **Whitelisting** : Valeurs autorisées pour statuts, rôles

### Protection multicouche

1. **Validation côté route** : express-validator bloque les inputs malveillants
2. **ORM Sequelize** : Requêtes préparées empêchent injections SQL
3. **Contraintes modèle** : Validation Sequelize en dernier recours
4. **Sanitisation** : trim(), normalizeEmail(), isURL()

### Ce qu'on évite complètement

- ❌ Requêtes SQL brutes avec concaténation
- ❌ Eval() ou Function() avec inputs utilisateur
- ❌ Insertion directe en BDD sans validation
- ❌ Regex dangereux (ReDoS)
- ❌ Désérialisation non sécurisée

### Résumé

Double protection : validation stricte des inputs + ORM sécurisé = zéro injection possible.
